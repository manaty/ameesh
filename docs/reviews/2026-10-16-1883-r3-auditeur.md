## B1 — validation finale non cohérente ; reprise non validée

`src/ameesh/accounts.py:1781-1793` relit les retenues puis les identités par deux appels séparés, hors verrou de placement. Une retenue peut être publiée entre ces appels : elle ne figure pas dans `frais` et le compte est rendu malgré elle. De plus, si la première cible est écartée, le résultat de `decide(frais, conflits_frais)` est rendu sans aucune validation nouvelle. La reprise peut donc choisir un autre compte dont une retenue vient d'apparaître pendant son classement.

Les deux cas sont reproduits par le [témoin](2026-10-16-1883-r3-auditeur-probe.py), en exécutant le vrai `choose` et le vrai `identity_conflicts` :

1. La deuxième lecture d'identités publie une retenue de `secondaire`, après la dernière lecture des retenues. Résultat : `chosen=secondaire`, `held_at_return=[secondaire]`.
2. La validation écarte `secondaire`. Pendant le `rank` de la reprise critique, une retenue de `primaire` est publiée. Résultat : `chosen=primaire`, `held_at_return=[primaire,secondaire]`, seulement deux lectures de retenues.

Le pilote avait demandé un point de validation cohérent **sous le même verrou** (événement du lot 30950, 16/10). Le verrou `account_active` de `switch_guarded` ne couvre ni ces lectures finales ni les retours de continuité/forçage/critiques. Une lecture supplémentaire isolée ne fournit pas le protocole commun demandé. Les nouveaux tests auteur, limités à deux jeux successifs de retenues, n'exercent pas ces publications intermédiaires.
