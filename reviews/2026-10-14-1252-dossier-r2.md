## 2. Ce que le lot change

- `vm.sh agents` gagne deux actions : **`installer [REF]`** et **`retour`** (dispatch
  fin de fichier ; validation des actions en tête). Le mode agents travaille dans le
  layout du compte `ameesh` (`~/.local/share/ameesh` : clone `src`, instantanés
  `src-<sha7>`, venv, `previous-sha`, journal `installation-en-cours`), un
  `BASCULE_ENV` par VM (`AGENTS_SSH`, `HOTE_AGENTS`).
- **Garde d'identité avant toute mutation** : `exiger_identite_agents` lit
  `AMEESH_HOST` de l'`EnvironmentFile` du compte runner (via `config.load().host`,
  avec repli qui reproduit la résolution sans importer le paquet si le venv est cassé)
  et refuse si la valeur ≠ `HOTE_AGENTS` — un `BASCULE_ENV` qui vise une autre VM
  n'écrit rien. Configuration illisible / host vide / non textuel ⇒ fermeture.
- **Garde migrations** : `exiger_migrations_agents` refuse l'installation si des
  versions de migration du commit visé manquent de la base commune du mesh
  (`poste.sh migrer` d'abord), même garde que le mode serveur.
- **Instantanés exacts** : `git worktree add --detach` du commit, nettoyage des
  artefacts ignorés, puis vérification **fichier par fichier** (SHA-1/mode/type,
  fichier en trop ou absent) contre les objets du commit, sans passer par l'index
  (`assume-unchanged`/`skip-worktree` ne masquent rien). Un instantané préexistant
  altéré fait refuser avant toute mutation ; il n'est jamais écrasé.
- **Journal de récupération** (`installation-en-cours`, 0600, `mktemp`+`mv`, refuse
  d'écraser) écrit **avant** la mutation : il retient le SHA quitté. `previous-sha`
  n'est publié qu'après une installation réussie. En cas d'échec de pip, `installer`
  ferme en conservant le journal ; `installer` refuse tant que le journal existe et
  oriente vers `retour`. `retour` privilégie le SHA du journal (marche même sans
  `previous-sha`), réinstalle, puis enchaîne `redemarrer` et `controler` ; après
  succès il laisse `previous-sha` sur le code installé (second `retour` idempotent).
- **Envoi du commit par paquet git** si la VM ne l'a pas : `paquet_git` exclut le HEAD
  du clone de la VM (prouvé présent par `tete_clone_distante`) au lieu de
  `^origin/main`, avec repli en paquet autonome si l'exclusion vide le paquet
  (corrige « Refusing to create empty bundle » pour une cible déjà fusionnée dans main).
  Réutilisé par l'`installer` du mode serveur.
- Documentation `docs/DEPLOIEMENT-HOTE-AGENTS.md` réécrite (section installer/retour,
  journal, instantanés, paquet git).
- Le commit de tête `4ac67f8f4` ne change **que le test** (`tests/test_1252_vm_agents_install.py`,
  +43/−40) : le harnais bâtit désormais son propre dépôt d'origine à 3 commits, car la
  CI fait un checkout en profondeur 1 (`HEAD~1` absent) — défaut de test dépendant de
  l'environnement corrigé à la source (canon §3).
- `tests/test_503_agent_host.py` : le cas qui attendait le refus de `installer` en mode
  agents passe à `publier` (l'action n'est plus refusée).

## 5. Points à instruire par le R2 (lecture du code à la tête, non prouvés par les tests)

À traiter comme des questions, pas comme des verdicts ; les numéros 1 et 2 sont les
plus sensibles.

1. **Relance d'`installer` sur le SHA déjà installé** (`vm.sh` étapes 3 et 9) :
   `avant` est lu dans `direct_url.json` du venv, donc si B est déjà installé,
   `complet=B`, le journal vise B et `previous-sha` est réécrit à **B** — la cible de
   retour A est perdue (A→B réussi, puis `installer B` ⇒ `retour` ne revient plus à A).
   Aucun test ne couvre la relance après une installation réussie (les tests de
   relance portent sur un journal d'échec présent). À qualifier : défaut à corriger ou
   comportement acceptable ?
2. **Lisibilité du paquet git par le compte `ameesh`** : `chmod 644` est fait **en
   local** avant `scp` ; le mode du fichier distant suit le umask du root distant à la
   création (un umask 077 rendrait `/tmp/ameesh.bundle` illisible pour `ameesh`, alors
   que le `git fetch` qui suit tourne sous `ameesh`). Le faux `scp` des tests préserve
   644, donc le chemin réel n'est pas prouvé. À prouver sur une VM réelle (témoin) :
   lecture effective du bundle, et nom fixe `/tmp/ameesh.bundle` écrit en root
   (pré-création/symlink) à vérifier.
3. **Aide tronquée** : le repli d'usage du mode serveur imprime `sed -n '4,28p'` alors
   que le paragraphe « En mode agents » ajouté va jusqu'à la ligne ~33 : l'aide coupe
   la phrase. (Le garde d'action inconnue en mode agents, lui, est correct : message
   clair + code 2.)
4. **Frontière « aucune mutation avant journal »** : le fetch/paquet git et les
   instantanés (worktrees) précèdent l'écriture du journal ; le code installé n'est
   touché qu'après. Confirmer que c'est la frontière voulue (les instantanés sont
   additifs, le bundle est retiré).
5. **Échec après pip réussi** : si l'écriture de `previous-sha` ou l'effacement du
   journal échoue, `installer` reste bloqué et `retour` ramène au code quitté alors que
   le pip a réussi — comportement fail-safe mais coûteux, à confirmer.
6. **Garde migrations et venv cassé** : `migrations_absentes_agents` avale les erreurs
   python (`|| true`), donc un venv cassé fait afficher « toutes les migrations
   absentes » (message trompeur) ; la commande ferme quand même (fail-closed).
7. **Comparaison d'hôte exacte** (`h = HOTE_AGENTS`) : FQDN dans l'`EnvironmentFile`
   contre nom court du registre (ou l'inverse) ⇒ refus. Vérifier la convention réelle
   des VM.
8. **Détails du vérificateur d'instantané** : le test de mode n'utilise que
   `S_IXUSR` ; la branche sous-module est inatteignable aujourd'hui (le dépôt n'a pas
   de `.gitmodules`).
9. **Couverture de tests** (43 cas, harnais hermétique avec faux ssh/scp/runuser/
   systemctl/pip ; vrai git) : pas de ssh/scp/pip/DB réels ; le repli « paquet
   autonome » n'est pas exercé (le test ne pose que `refs/remotes/origin/main`, que le
   nouveau code ignore) ; `AGENT_MESH_HOST`/`AGENT_MESH_CONFIG` non testés (seul
   `AMEESH_CONFIG` l'est) ; mode du journal non vérifié.
